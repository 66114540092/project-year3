# 3.5 แผนภาพคลาสระดับโดเมน (Domain Model Class Diagram)

การออกแบบโครงสร้างคลาสในบทนี้ มุ่งเน้นไปที่ **แผนภาพคลาสระดับโดเมน (Domain Model)** ซึ่งทำหน้าที่เป็นพิมพ์เขียวของฐานข้อมูลและตรรกะทางธุรกิจหลัก (Core Business Logic) ของระบบ BattleHub โดยแผนภาพนี้จะแสดงความสัมพันธ์ระหว่างเอนทิตี (Entity Relationship) และข้อกำหนดของข้อมูล (Data Constraints) ในรูปแบบของ Django Models เพื่อให้สอดคล้องกับสถาปัตยกรรมแบบ Model-View-Template (MVT) ของ Django Framework โดยมีการตัดส่วนของ View และ Template ออกเพื่อให้ภาพรวมของโครงสร้างข้อมูลมีความชัดเจนที่สุด

## รายละเอียดคลาสและโครงสร้างข้อมูลภายในระบบ

### 1. ส่วนจัดการตัวตนและบัญชีผู้ใช้งาน (Accounts & Identity Management)
ในส่วนนี้รับผิดชอบการเก็บข้อมูลผู้ใช้งานและการสืบทอดสิทธิ์ (Authorization) ภายในระบบ

*   **User (Django Built-in Model):** คลาสมาตรฐานของ Django ที่ถูกนำมาปรับใช้เป็นหัวใจหลักในการยืนยันตัวตน ประกอบด้วยคุณลักษณะ (Attributes) ได้แก่ username, email, password (ที่ถูกเข้ารหัสแบบ PBKDF2) และสถานะบัญชี is_active รวมถึง is_staff ที่ใช้ในการจำแนกสิทธิ์ระหว่างผู้ใช้งานทั่วไปและผู้ดูแลระบบ
*   **Profile (User Extension Model):** ถูกออกแบบมาเพื่อเก็บข้อมูลส่วนขยายที่มีความสัมพันธ์แบบ One-to-One (1:1) กับ User คลาสนี้ทำหน้าที่เก็บข้อมูลเชิงพรรณนา ได้แก่ avatar (ImageField) สำหรับรูปภาพประจำตัว และ bio (TextField) สำหรับข้อความแนะนำตัว โดยมีการใช้ Django Signals (post_save) ในการสร้างออบเจกต์ Profile อัตโนมัติทันทีที่มีการสมัครสมาชิกใหม่ เพื่อรับประกันความสอดคล้องของข้อมูล (Data Integrity)

### 2. ส่วนโครงสร้างทัวร์นาเมนต์ (Tournament Architecture)
เป็นส่วนที่ทำหน้าที่กำหนดกฎเกณฑ์และสถานะของการแข่งขันในระบบ

*   **Tournament (Core Entity):** เป็นศูนย์กลางของระบบที่เชื่อมโยงทุกออบเจกต์เข้าด้วยกัน ประกอบด้วยข้อมูลสำคัญคือ:
    *   `bracket_size`: กำหนดขนาดของการแข่งขัน ($2^n$) ได้แก่ 2, 4, 8 หรือ 16 คน
    *   `pin_code`: รหัสผ่าน 6 หลักที่ถูกสร้างขึ้นแบบสุ่ม (Randomized) สำหรับการเข้าถึงห้องพักรอ (Lobby)
    *   `status`: สถานะของการแข่งขัน (State Machine) ที่ประกอบด้วย DRAFT, WAITING, OPEN และ FINISHED เพื่อใช้ควบคุมลำดับการทำงาน (Workflow) ของระบบ
*   **Competitor (Competitor Metadata):** เก็บข้อมูลของผู้เข้าแข่งขันที่ถูกนำเข้าสู่ระบบ มีความสัมพันธ์แบบ Many-to-One (N:1) กับ Tournament โดยข้อมูลที่สำคัญคือชื่อและรูปภาพที่เป็นไฟล์สื่อ (Media Files) ซึ่งจะถูกนำไปใช้ในกระบวนการจับคู่แข่งขันแบบอัตโนมัติ

### 3. ส่วนเครื่องยนต์การจับคู่และการลงคะแนน (Match & Voting Engine)
ส่วนนี้เป็นตรรกะหลักที่ใช้ในการประมวลผลคะแนนและการตัดสินผู้ชนะในแต่ละรอบ

*   **Match (Match Management):** คลาสที่เก็บข้อมูลการจับคู่แบบ 1 ต่อ 1 ในแต่ละลำดับการแข่งขัน ประกอบด้วยความสัมพันธ์กับ Competitor สองราย และมีการเก็บข้อมูล round_number เพื่อใช้ในการคำนวณตำแหน่งภายใน Bracket โดยคลาสนี้จะมีตรรกะในการระบุผู้ชนะ (winner) หลังจากสิ้นสุดเวลาโหวต
*   **MatchVote (Transactional Record):** ทำหน้าที่บันทึกการลงคะแนนของผู้ใช้งานแต่ละรายต่อแมตช์การแข่งขัน โดยมีการกำหนดข้อกำหนด Unique Together Constraint ระหว่าง match และ user ในระดับฐานข้อมูล เพื่อป้องกันการลงคะแนนซ้ำ (Double Voting) และเพื่อให้ระบบสามารถอัปเดตคะแนนแบบ Near Real-time ผ่านกลไก AJAX Polling ได้อย่างถูกต้อง
*   **Participant (Session Control):** คลาสที่ใช้จัดการสถานะของผู้เข้าร่วมในห้อง Lobby โดยใช้ session_key เพื่อติดตามการเชื่อมต่อแบบชั่วคราว ทำให้ระบบสามารถรองรับทั้งสมาชิก (Member) และบุคคลทั่วไป (Guest) ในการเข้าถึงห้องแข่งผ่านรหัส PIN ได้

### 4. ส่วนการกำกับดูแลและความปลอดภัย (Moderation & Security)
ส่วนที่ช่วยให้ผู้ดูแลระบบสามารถรักษาความสงบเรียบร้อยและตรวจสอบการทำงานย้อนหลังได้

*   **Report (Moderation Tool):** ถูกออกแบบมาให้มีความยืดหยุ่นสูง (Generic-like Relationship) โดยใช้การสร้าง Nullable Foreign Keys เพื่อเชื่อมโยงไปยังเป้าหมายที่หลากหลาย เช่น รายงานผู้ใช้งาน (User), รายงานทัวร์นาเมนต์ (Tournament) หรือรายงานแชทที่ไม่เหมาะสม (MatchComment) เพื่อส่งข้อมูลเข้าสู่ Admin Dashboard สำหรับการพิจารณาคดี (Resolution)
*   **AuditLog (Activity Tracking):** คลาสสำหรับจัดเก็บหลักฐานการกระทำ (Evidence of Actions) ของผู้ดูแลระบบ ประกอบด้วยข้อมูล action_type, timestamp และ ip_address เพื่อสร้างระบบ Audit Trail ที่มีความโปร่งใสและสามารถตรวจสอบย้อนหลังได้หากเกิดความผิดพลาดในระบบ
